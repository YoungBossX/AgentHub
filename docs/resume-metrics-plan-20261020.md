测量包含未提交修复，不能只用 HEAD 代替完整版本。当前运行时代码和操作器的222项冻结哈希已重新核验。
本次没有提交、推送、迁移产品库或追加付费模型批测。

## 结论

优先展示“解决什么具体问题、采用什么机制、在什么条件下有什么结果”。
AgentHub 最值得准备的是上下文控制、可复现的任务完成率、故障恢复和事件一致性。
模型 Token 与单位成功任务成本有价值，但当前缺少可信使用量，必须补采后再写。
不要为了简历把 SQLite 改成 PostgreSQL，或把 HTTP 接口吞吐量当成多 Agent 编码吞吐量。

现阶段最直接的量化亮点是：同一个实际超限请求的应用管理输入由540,911降至22,242字符，
减少95.9%。这来自一个真实失败样本的离线重建，本次在当前代码上复现，不能写成所有请求、
Token、费用或推理耗时降低95.9%。

| 优先级 | 指标与价值 | 当前能否取得 | 采集要求 |
| --- | --- | --- | --- |
| P0 | 首次完整验收率、限定重试后的完成率，证明系统实际能交付 | 已有初版框架和真实小样本，需要修复后同版扩样 | 中文5类每类10个固定实例，共50个；规划、编码、Diff、源码绑定检查、业务断言均需通过；超时计失败。探针、受控故障和失败后的补修分开 |
| P0 | 上下文治理前后体积及超限率，解释优化的因果链 | 一个真实失败样本已验证；代表性不足 | 固定短/中/长历史，同源快照对照；记录字符、UTF-8字节、被省略日志数量和必须保留项；如增加真实对照，单独统计任务效果 |
| P0 | 故障恢复率与回放完整性，证明后端可靠性 | 现有故障注入和回放测试可扩展，400事件试验已完成 | 固定模型失败、超时、中断、SSE断线、工作进程退出等矩阵；写明每种分母、恢复预算、重复或缺失事件数、最终状态；不可用少量通过外推生产可靠性 |

| P1 | 单次与单位成功任务 Token、估算费用，体现投入产出 | 当前无法可靠获取，需要专门补采 | 允许字段采集 Provider 原始 usage，区分输入/输出/缓存、模型、重试及失败调用。缺失记null；单位成功成本必须包含失败消耗。订阅与转发价格不能按其他模型标价推算 |
| P1 | 文件范围收尾开销，体现本地性能优化 | 有历史成对脚本证据，需要增强 | 固定文件数、字节数、Git状态与检查策略；两版交替多次，建议至少30对，保存原始样本、分位数与环境负载。只是收尾开销，不是模型加速 |
| P2 | 控制面 API 吞吐与延迟 | 可用独立负载实验取得，但与 Agent 能力关联较弱 | 健康检查、会话列表、事件读取分别标注路由和载荷；不能把结果写成“同时运行X个编码Agent” |
| 不优先 | 通用 Recall@K、日活、真实用户规模、生产可用性 | 当前没有相应标注集或真实业务流量证据 | 记忆检索若要测召回，先建立人工相关性标签；不能把无用户本地 demo 写成已上线平台 |

50个中文固定实例建议包含后端健康检查、多文件修改、联系人前后端协作、两轮追问、第五类正常小改动。
受控故障另建分母，不能把必然先失败的注入任务混入普通首次成功率。
同版冻结源码、实例输入、初始目标提交、模型配置别名、预算及独立验收器。预先定义最大耗时与重试，
全部失败留档，按每类及总体报告分子/分母；若模型实际型号无法核实，就仅记录配置别名。
需要比较“优化后提升多少”时，两版必须使用匹配样本及相同预算；只跑修复版无法得出提升百分点。

耗时定义参考 [Grafana k6 官方指标](https://grafana.com/docs/k6/latest/using-k6/metrics/reference/)：
HTTP请求时延有自己的边界，不能当作完整 Agent 任务时延。
费用还需区分本地估算与真实账单；[Claude Code 官方费用说明](https://code.claude.com/docs/en/costs)
同样区分二者。该说明不提供本项目 Ark 转发/订阅服务的实际计价证据。

## 源码核对发现的指标缺口

- `claude_code_adapter.py`当前结果映射不持久化完整原始 usage/成本回执；不能从文本字符数推导 Token 或费用。
- 最早的`message.delta`可能含非正文事件；未经事件类型筛选不能称为模型首 Token 耗时。
- `memory_rehearsal.py`是确定性离线演练，部分一致性值来自构造的相同快照；不能写成真实 Agent 记忆正确率100%。
  真实回执至多证明输入绑定了哪份冻结记忆，要证明理解、遵循和任务收益还需独立判定与对照。
- 真实联系人预览使用操作者辅助的固定 ASGI 桥接，不能写成平台已完成任意前后端应用的原生联合部署。

以上是证据采集或既有能力边界，不在本次研究任务中擅自增加新功能。

## 当前可用的四条候选表述

下列是候选文案，具体个人职责仍应与本人能解释和复现的工作一致。
本项目有 AI 辅助开发和测试，不能将“实现机制”自动扩写为全部代码手写或独立原创。

1. 上下文治理：针对多轮任务历史事件挤占 Planner 输入的问题，分离完整过程记录与有界规划摘要；在一个实际超限请求的离线重建中，将应用管理输入从54.1万降至2.22万字符，减少95.9%，保留原始日志与省略证据。
2. 事件一致性：基于持久化事件与游标恢复任务进度，修复 SQLite 并发事件序号竞争；本地4进程共400次写入无序号冲突，400条分页回放及中途游标续读结果一致。
3. 验收闭环：将任务完成判定与真实 Diff、文件修改范围、源码版本绑定检查和独立业务断言关联；联系人协作样例覆盖24项前后端业务检查，保存真实失败、追加修复及复验过程。
4. 多 Agent 协作：打通自然语言规划、前后端任务依赖、独立只读 QA 与可视化过程回放，建立中文真实 API 评测和过程、Diff、预览证据链，区分模型完成、评审通过与业务验收通过。

正式简历建议保留两项最强量化证据，其他条目突出机制。不要把85/85规则回归、
12份模型QA报告或400条小事件当作通用任务成功率、业务规模或生产稳定性。
