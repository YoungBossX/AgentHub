## 发现的问题与修复

1. 有效引号文案后附“保留其他行为”等约束，被当成无效标题，未调用已配置的群组
   Planner；换行后的约束可能被规则忽略，否定创建要求还可能误入应用模板。
   先复现失败，再把完整请求分成有效简单槽位、需 Planner 的完整槽位加约束、无效槽位。
   文案解析和应用创建入口沿用同一边界，不截断执行；缺失、超长、未闭合及非写请求仍拒绝。
2. 真实原生 QA 合法列出待审文件时，一次受限修复要求只读任务的 `plannedFiles` 必须为空，
   导致计划被误拒绝。现仅允许只读任务列出该目标原本绑定的文件，显式要求 `readOnly=true`；
   仍不允许 QA 修改文件或引用其他目标/配置。
3. 修复计划被拒绝后，数据库已中断排队运行，报告却保留 `queued`；规划实际已成功，
   也可能被报告为未观察到。现先记录真实规划来源，收尾仅刷新尚未终态的尝试并保留
   `stateAtCutoff` 与停止来源，已完成阶段的原版本和结果不改写。
4. 实际业务库仍为v1，当前代码启动要求v2。只读预检确认没有监听API或运行中任务，
   沿用此前用户本地迁移授权，使用现有离线工具完成E盘备份、副本演练和实际升级。
   26表830条旧记录及BLOB逐值相等，完整性、外键与事件序号检查通过；新副本ASGI启动、
   `/health` 返回database=ready并正常关闭。实际业务服务未常驻启动。

开发侧独立审查发现的换行、否定创建和无效槽位组合先补失败回归再修复，最终只读复核无阻断。
没有增加 Adapter、工具权限、依赖或迁移版本；实际库使用已有v2迁移。单角色 frontend 的既有 Planner 路由
限制保持；本次原失败和真实修复均通过显式群组入口。
